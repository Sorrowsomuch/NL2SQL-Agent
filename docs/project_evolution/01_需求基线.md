# 需求基线

## 项目目标

DataAnalyze 的目标是把自然语言问题转成安全、可执行、可审计的数据库分析结果，并通过 `/chat` 稳定返回：
- 文本结论
- 结构化查询结果
- 图表配置
- 可追踪的调试与审核信息

当前核心演进方向有三条：
- 让 `executor` 能处理更复杂的生产查询，尤其是多表、聚合、趋势、排序和时间窗口分析。
- 避免整库 schema 一次性塞给 LLM，改成渐进式获取和渐进式使用。
- 建立字段语义知识层，解决字段名和真实业务含义不一致时的理解问题，并逐步进入 SQL 规划。

## 已确认的硬约束

- 保持 SQL 只读护栏不变。
- 保持 `/chat` 响应 schema 向后兼容。
- 行为变化时要补充或更新 metrics 与 `review_debug`。
- 每完成一个阶段都要给出编译或测试证据，以及改动文件摘要。

## 当前已落地能力

- 结构化 schema 元数据层
- schema 元数据缓存与 PostgreSQL 查询下推
- 两段式 schema 获取
- `postgres_schema_loader.py` 与 `schema_selection.py` 解耦
- 本项目作用域 allowlist / denylist
- SQL guard 与 aggregate/window repair
- 记忆压缩与事实提取的 `LLM + fallback`
- 本地知识库目录、加载器与本地检索器
- 可选的 Ollama `bge-m3` 混合召回
- 第一阶段意图级 query planner
- 字段级知识接线
- query-aware 列保留
- 第二阶段精确字段 planner

## 当前最重要的产品诉求

- 不只要选对表，还要保留足够的辅助分析字段。
- 避免列裁剪过度导致分析偏差。
- 让知识层逐步进入 SQL 规划，而不只是召回层。
- 让 query planner 在表阶段前移，避免候选表过早缩窄。
- 在混合数据库环境下，尽量稳定排除无关项目表。
- 继续减少 `_load_schema_metadata_from_postgres()` 的重型获取成本。

## 当前约束补充

- 不为了 planner 引入难以审计的黑盒字段选择逻辑，必须保留系统约束层。
- 不为了临时提效把默认列配置堆得过重，避免项目逐步臃肿。
- 不因为引入 planner 破坏现有回退链路；LLM 不可用时必须还能回到当前 query-aware 列保留。

## 当前不追求的事项

- 现在不把 LLM Wiki 作为在线请求链路的一环。
- 现在不急着把知识检索直接迁移到 `pgvector` 持久化检索。
- 现在不放开 SQL 护栏去支持 `WITH` 开头的 CTE。

## 当前验收口径

一次能力升级至少应满足：
- 不破坏 `/chat` 现有返回结构。
- 不削弱 SQL 只读护栏。
- 通过现有测试，或补充覆盖新行为的测试。
- 在 `review_debug` 或 metrics 中留下足够的观测证据。
- 用中文文档说明“做了什么、为什么做、后面还差什么”。
