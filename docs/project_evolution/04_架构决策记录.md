# 架构决策记录

## ADR-001：Schema 获取拆成两段式

决策：
- 不再默认整库加载详细 schema 给 LLM
- 采用“轻量表发现 + 候选表详情加载”

原因：
- 降低 prompt 膨胀风险
- 为后续 planner 和 skill 化保留清晰边界

## ADR-002：Schema 相关代码按职责解耦

决策：
- `db_tool.py` 保留编排层职责
- `postgres_schema_loader.py` 承担 PostgreSQL 元数据加载
- `schema_selection.py` 承担规则选择逻辑

原因：
- 提高可读性和可审计性
- 避免主文件持续膨胀

## ADR-003：字段选择采用“LLM 参与 + 系统约束回写”

决策：
- 不采用“每表大量默认辅助列”的长期方案
- 不采用“字段选择完全交给 LLM”的黑盒方案
- 采用“规则保底 + 字段 planner + 系统预算/存在性约束”的折中架构

原因：
- 避免配置膨胀
- 避免不可审计
- 为后续 skill 化保留清晰边界

## ADR-004：Query Planner 前移到表阶段

决策：
- 新增第一阶段意图级 query planner
- 它只规划语义需求和候选表，不输出精确字段名
- 第二阶段字段 planner 保留，负责精确字段落地

原因：
- 真正的问题在“规划发生得太晚”，而不只是字段裁剪太机械
- 如果候选表在前面就缩窄错了，字段 planner 无法补救
- 两阶段 planner 比“一次性全交给 LLM”更稳、更可审计

当前含义：
- 第一阶段 planner 影响 `detail_tables` 和最终候选表范围
- 第二阶段 planner 只在详细 schema 范围内选精确字段
- query-aware 规则层继续保留为 fallback
## ADR-005：Perfetto trace 分析先作为独立工具链落地

日期：2026-05-14

### 决策

新增 `PerfettoTool`，先通过独立接口 `/perfetto/query` 和 `/perfetto/analyze` 跑通 `output.pb` 分析，而不是立即把 Perfetto 能力并入 `/chat` 的 PostgreSQL Executor 主链路。

### 原因

- Perfetto 的数据源是 trace 文件，不是 PostgreSQL 数据库；查询执行由 Trace Processor 完成。
- Perfetto SQL 的表、单位、解释口径和业务库 SQL 不同，尤其 `ts/dur` 默认是纳秒。
- 先用独立工具能快速验证 `output.pb -> SQL -> rows -> metrics -> conclusion` 是否成立。
- 避免在 MVP 阶段污染现有 `DatabaseTool`、schema planner 和 Reviewer 规则。

### 当前实现

- `PerfettoTool` 默认读取仓库根目录 `output.pb`。
- `execute_sql()` 只允许只读 Perfetto SQL。
- `analyze_problem()` 先通过模板选择 SQL：
  - `long_slice`
  - `cpu_time`
- `main.py` 暴露：
  - `POST /perfetto/query`
  - `POST /perfetto/analyze`

### 后续取舍

后续接入 agent 时，优先采用“数据源路由 + 模板候选 + 受限 SQL 改写”的方式，而不是让同一个 Executor 在同一个 prompt 中同时面对 PostgreSQL schema 和 Perfetto schema。

## ADR-006：Perfetto 链路保留 trace 入库与多 dataset 演进能力

日期：2026-05-14

### 决策

当前阶段仍然直接通过 Trace Processor 查询 `output.pb`，但 Perfetto Agent 的设计必须预留数据源替换能力。后续可以把多份采集 trace 的核心数据抽取到 PostgreSQL，再让同一套 agent 链路查询数据库中的 trace dataset。

### 原因

- 后续可能有很多采集数据，不能长期只绑定仓库根目录单个 `output.pb`。
- 前端需要稳定联调接口，不应该随着底层从文件查询切到数据库查询而频繁改调用方式。
- 直接查 `output.pb` 适合快速验证和单 trace 分析；入库后更适合历史归档、多 trace 对比、批量指标统计。
- Perfetto SQL 和入库后的 PostgreSQL SQL 不完全一致，因此需要在数据源层隔离差异。

### 设计约束

- Agent 层面向 `dataset_id` / `trace_id`，不要直接面向文件路径。
- 当前默认 dataset 可以指向本地 `output.pb`。
- 数据源接口至少需要支持：
  - schema/context 获取。
  - SQL 或模板查询执行。
  - 指标结果标准化。
- 前端优先接入稳定接口：
  - `POST /perfetto/agent`
  - `POST /perfetto/analyze`
  - `POST /perfetto/query`
  - 后续 dataset 管理接口。

### 后续实现方向

先实现 `TraceProcessorPerfettoSource`，后续增加 `DatabasePerfettoSource`。`PerfettoAgent` 只依赖抽象数据源，不关心结果来自 `output.pb` 还是已入库表。
