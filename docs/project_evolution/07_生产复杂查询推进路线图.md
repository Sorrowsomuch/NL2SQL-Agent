# 生产复杂查询推进路线图

## 目标

这份路线图用于回答一个实际问题：当前 DataAnalyze 已经具备中等复杂度查询能力，但距离“稳定处理生产环境复杂查询”还有哪些关键缺口，以及应该按什么顺序推进。

这里的“生产复杂查询”主要指：

- 多表关联查询
- 指标口径复杂的分析查询
- 需要趋势、分布、TopN、明细混合判断的查询
- 字段命名不直观、需要依赖业务语义知识的查询
- 需要稳定处理空结果、时间窗口、历史数据分布差异的查询

## 当前能力判断

当前系统已经较稳地支持：

- 单表查询
- 基础聚合、分组、排序、TopN
- 基础时间趋势查询
- 1 到 2 张表的基础关联查询
- 依赖知识库进行选表、选字段的中等复杂度查询

当前系统仍不够稳的场景：

- 多事实表、多跳 join 的复杂查询
- 依赖复杂指标口径定义的查询
- 库大、表多、同义表多时的稳定选表
- 复杂子查询、复杂窗口函数组合
- 生产知识未覆盖、字段语义又不直观的查询

结论：

- 当前适合联调、灰度验证和中等复杂度查询
- 还不适合直接承诺“稳定覆盖生产环境复杂查询”

## 推进原则

- 先补“查询规划层”，再补“字段层”和“SQL 形态层”
- 先补最影响生产稳定性的能力，再补增强项
- 保留现有只读 SQL 护栏，不以放松安全边界换能力
- 保留 fallback，避免一次性把主链路切成纯黑盒
- 每个阶段都需要可观测、可测试、可回归

## 阶段 1：补齐 SQL Planner

### 目标

让系统先规划“怎么查”，而不是只停留在“先选表再补字段”。

### 要做的事

- 在当前 query planner 和 field planner 之上增加 SQL planner
- 规划内容至少包括：
  - 查询类型
  - 主指标
  - 分析维度
  - 过滤条件
  - join 策略
  - 聚合层次
  - 是否需要子查询
- 保留当前规则 fallback，不把 SQL 规划完全交给 LLM

### 完成标准

- 趋势、分布、TopN、明细、确认类查询能稳定生成不同 SQL 形态
- SQL 生成不再主要依赖 prompt 自由发挥

## 阶段 2：让 query_pattern / metric_definition 真正驱动 SQL

### 目标

让知识层不只影响召回和 planner 输入，而是直接影响 SQL 规划策略。

### 要做的事

- 把 query pattern 中的推荐表、推荐字段、推荐过滤条件、推荐 group by 接入 SQL planner
- 把 metric definition 中的指标口径、时间列、默认过滤条件接入 SQL planner
- 为高频分析模式建立稳定落地路径

### 完成标准

- “趋势”“TopN”“分布”“确认型”这类常见问法能稳定走到对应 SQL 形态
- 指标口径不再完全靠模型猜测

## 阶段 3：补厚生产知识库

### 目标

降低“字段名与真实业务含义不一致”带来的误判。

### 优先补的知识类型

- table_profile
- column_semantics
- metric_definition
- query_pattern
- relationship_hint

### 优先覆盖范围

- 高频查询表
- 字段语义最绕的表
- 最容易问错的指标
- 最常见的 join 路径

### 完成标准

- 覆盖生产高频分析问法的 60% 到 80%
- 字段语义误判率明显下降

## 阶段 4：增强多表 Join 规划

### 目标

让系统不仅知道“哪些表有关联”，还知道“该怎么连、为什么连、连到什么程度”。

### 要做的事

- 区分主事实表、维表、辅助表
- 增强多跳 join path 选择
- 增强相似表判别
- 减少无意义联表和噪音 join

### 完成标准

- 2 到 3 张表的生产风格查询明显更稳
- 不再频繁误选辅助表或产生冗余 join

## 阶段 5：补时间窗口与空结果智能化

### 目标

减少“SQL 本身是对的，但因为时间窗口或数据分布问题被误判失败”的情况。

### 要做的事

- 更智能地处理“最近 N 天 / 最近 N 小时”
- 在必要时支持基于数据最大时间回看
- 区分“空结果是失败”与“空结果本身就是结论”
- 减少无意义重试

### 完成标准

- 样例库、历史库和在线库在时间窗口处理上更稳
- 趋势查询和确认类查询误拒绝明显下降

## 阶段 6：增强复杂 SQL 形态支持

### 目标

把当前中等复杂度查询能力推进到更接近生产复杂度。

### 要做的事

- 增强子查询规划
- 增强复杂聚合和窗口函数组合稳定性
- 在保持只读护栏不变的前提下支持更丰富的 SELECT 形态

### 完成标准

- 更复杂的子查询、聚合改写、窗口分析成功率更高
- 安全边界保持不变

## 阶段 7：建立生产回归集

### 目标

不靠感觉判断系统是否接近生产可用，而是通过固定回归集量化能力。

### 要做的事

- 整理一批真实风格 query
- 覆盖：
  - 单表
  - 双表
  - 多表
  - 趋势
  - TopN
  - 分布
  - 空结果
  - 字段语义复杂场景
- 固化期望结果，或至少固化期望 SQL 特征和审核结果

### 完成标准

- 每次改 planner、知识库、护栏都能跑回归
- 能明确判断能力提升还是回退

## 建议执行顺序

1. 补齐 SQL planner
2. 让 query_pattern / metric_definition 深度接入 SQL 规划
3. 补厚生产知识库
4. 增强多表 join 规划
5. 优化时间窗口与空结果策略
6. 增强复杂 SQL 形态支持
7. 建立生产回归集

## 为什么这样排序

- 当前最大短板已经不是字段层，而是查询规划层
- 因此先补 planner，收益最大
- 知识库应围绕 planner 和高频查询成长，而不是先无限扩知识条目
- join、时间窗口、复杂 SQL 形态，是往生产可用进一步推进的增强项
- 回归集必须放到后面固化，否则每次改完都只能靠体感判断

## 阶段验收建议

- 阶段 1 完成后：中等复杂查询明显更稳
- 阶段 3 完成后：字段语义误判明显下降
- 阶段 4 完成后：多表查询开始接近生产可用
- 阶段 7 完成后：才适合正式讨论生产 readiness
## 2026-05-14 补充：Perfetto trace 性能分析路线

Perfetto trace 分析和 PostgreSQL 生产复杂查询共享“问题 -> SQL -> 指标 -> 结论”的目标，但两者的数据源、schema、单位和审核重点不同，因此需要单独推进。

### 当前能力判断

已具备：

- 能通过 Trace Processor 查询 `output.pb`。
- 能执行用户提供的 Perfetto SQL。
- 能通过模板完成长耗时 slice 和 CPU time 的初步分析。
- 能返回结构化 metrics、evidence、conclusion。

仍不足：

- 模板覆盖面很窄。
- 尚未把 Perfetto 知识沉淀为可检索知识库。
- 尚未接入 agent 的问题识别、SQL 选择和 Review 机制。
- 结论仍是规则模板级别，不能替代完整性能根因诊断。

### 推进原则

- 先模板化，再放开 LLM 改写。
- 先保留 evidence，再生成 conclusion。
- 所有耗时指标必须明确 ns -> ms 的转换。
- 空结果必须给出“无异常证据”或“模板不适用”的区别。
- Perfetto 链路独立演进，稳定后再接入 `/chat` 或统一 agent 编排。

### 建议阶段

1. 模板扩充。
   - long slice。
   - CPU time。
   - frame/jank。
   - counter。
   - scheduling latency。

2. Perfetto 知识库。
   - 表语义。
   - 指标定义。
   - SQL 模板。
   - 结论阈值。

3. Agent 接入。
   - 识别 trace 性能问题。
   - 选择模板。
   - 在模板范围内生成/修正 SQL。
   - 汇总指标与证据。

4. Reviewer 接入。
   - SQL 安全。
   - 单位校验。
   - evidence 完整性。
   - conclusion 支撑性。

5. 回归集。
   - 固定 `output.pb` 样例。
   - 固定问题集。
   - 固定预期 SQL 特征和指标字段。

### trace 入库后的路线

Perfetto 链路后续需要支持多份采集数据，因此需要从“单文件即时查询”演进到“dataset 管理 + 数据抽取 + 数据库查询”。

建议顺序：

1. dataset 登记。
   - 保存 `dataset_id`、trace 文件路径、采集时间、设备/应用信息、备注。

2. 核心表抽取。
   - 先不要全量镜像 Perfetto 所有表。
   - 优先抽取常用事实：
     - long slice 明细。
     - CPU time 聚合。
     - frame/jank 明细。
     - counter 趋势采样或聚合。

3. 指标表沉淀。
   - 每个 dataset 产出稳定指标，例如 max_duration_ms、long_slice_count、top_cpu_thread。
   - 支持跨 dataset 对比。

4. 数据源切换。
   - 单 trace 深挖继续走 Trace Processor。
   - 多 trace 汇总和历史对比走数据库。

5. Agent 统一入口。
   - 前端仍调用同一个 `POST /perfetto/agent`。
   - 后端根据 `dataset_id`、问题类型和数据是否已入库选择 `trace_processor` 或 `database`。
