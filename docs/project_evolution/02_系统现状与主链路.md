# 系统现状与主链路

## `/chat` 当前主链路

一次 `/chat` 请求当前按下面顺序执行：

1. `main.py` 接收请求并调用 `WorkflowEngine.process(...)`
2. `WorkflowEngine` 先写入用户消息，并按 `session_id` 懒加载记忆
3. `compress_context()` 和 `extract_facts_if_needed()` 完成记忆压缩与事实提取
4. `Executor` 构建上下文并调用 `DatabaseTool.select_schema_context()`
5. `select_schema_context()` 当前已经升级为“两阶段 planner + 两段式 schema 获取”
   - 轻量表发现
   - 项目作用域过滤
   - 知识召回
   - 第一阶段 query planner
   - 候选表缩圈
   - 候选表详情加载
   - 关系扩展
   - 第二阶段字段 planner
   - 局部 schema prompt + knowledge prompt
6. `Executor` 生成 SQL，先过本地 SQL guard，必要时 repair，再执行
7. `Executor` 生成文本分析与图表
8. `Reviewer` 做规则审核和可选 LLM 复核
9. `WorkflowEngine` 根据 review 结果决定结束或重试

## 当前 schema / planner 主链路

当前 schema 相关主链路不是“规则缩圈后直接裁列”，而是：

- 第一阶段：意图级 query planner
  - 规划 `query_type`
  - 规划 `primary_metric`
  - 规划 `analysis_dimensions`
  - 规划 `filter_dimensions`
  - 规划 `candidate_tables_hard`
  - 规划 `candidate_tables_soft`
  - 规划 `join_needed`
- 第二阶段：精确字段 planner
  - 在候选表详细 schema 范围内，把第一阶段语义需求落到真实字段
  - 仍由系统做存在性校验、保底列补齐和预算裁剪

当前 query-aware 规则层仍保留，但已经降级为 fallback / 保底层。

## 字段选择现状

当前字段选择顺序是：

- 系统保底列
  - 主键
  - 关系列
  - 时间列
- 第一阶段 query planner 提供的分析需求
- 第二阶段字段 planner 提供的 `required / optional` 字段
- 原有 query-aware 规则优先级
- 原始列顺序补预算

这意味着：

- 现在不再只靠规则或只靠字段知识保列
- 也不是把字段选择完全交给 LLM
- 而是“planner 参与 + 系统约束回写”

## 代码职责边界

- `db_tool.py`
  - 编排层，负责主链路串联、缓存、作用域、planner 调用、SQL 执行和护栏
- `postgres_schema_loader.py`
  - 基础设施层，负责 PostgreSQL schema 轻量发现与详细元数据加载
- `schema_selection.py`
  - 规则策略层，负责排序、关系扩展、局部 schema 裁剪等 fallback 逻辑
- `query_planner.py`
  - 第一阶段意图级 planner 逻辑
- `field_planner.py`
  - 第二阶段精确字段 planner 逻辑
- `knowledge_retrieval.py`
  - 知识召回层

## 当前清理状态

- `use_mock` 已从 `/chat` 请求、workflow、executor 和 db_tool 执行链路中移除
- SQL 执行统一走真实 PostgreSQL 只读路径
- `/sessions` 列表接口已删除
- `/sessions/{session_id}/memory` 仍保留，供调试页查看单个会话记忆
- `workflow_events` 仍保留在 `/chat` 响应中，当前只是不再前端重点展示

## 当前主要优势

- 表阶段和字段阶段都已经有 planner，查询规划前移
- 混合数据库环境下已经能先做项目作用域收敛
- SQL 只读护栏仍然清晰稳定
- planner 层与系统约束层已经分开，便于审计

## 当前主要痛点

- 第一阶段 query planner 还是意图级 planner，不是完整 SQL planner
- `query_pattern` / `metric_definition` 已进入 planner 输入，但还没完整进入 SQL 生成策略层
- 空结果与时间窗口策略仍然偏弱
- 大库场景下详细 schema 加载仍需继续优化
## 2026-05-14 补充：Perfetto/output.pb 当前链路

当前系统除原有 `/chat` PostgreSQL 数据分析主链路外，新增了独立的 Perfetto trace 调试与模板分析链路。该链路面向仓库根目录的 `output.pb`，默认不依赖 PostgreSQL，也不依赖 Ollama/LLM。

### `/perfetto/query`

用途：直接执行用户给出的 Perfetto SQL，适合调试 trace 表结构和验证 SQL。

当前调用链：

1. `main.py` 接收 `POST /perfetto/query`，请求体使用 `PerfettoQueryRequest`。
2. 接口调用全局 `perfetto_tool.execute_sql(request.sql)`。
3. `PerfettoTool.execute_sql()` 执行只读护栏：
   - SQL 不能为空。
   - 不允许 SQL 注释。
   - 不允许 `INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE/CREATE/GRANT/REVOKE/ATTACH/DETACH`。
   - 最后一条语句必须是 `SELECT` 或 `WITH`。
   - 前置语句只允许 `INCLUDE PERFETTO MODULE ...`。
4. `_get_processor()` 创建或复用 `perfetto.trace_processor.TraceProcessor`，加载 `output.pb`。
5. `_execute_perfetto_query()` 调用 `processor.query(sql)`。
6. 查询结果被转换为统一结构：`sql / row_count / columns / rows / source=perfetto / duration_ms`。

### `/perfetto/analyze`

用途：把“性能问题 -> SQL -> 指标 -> 结论”的最小闭环跑通。当前是模板分析，不调用 LLM。

当前调用链：

1. `main.py` 接收 `POST /perfetto/analyze`，请求体使用 `PerfettoAnalyzeRequest`。
2. 接口调用 `perfetto_tool.analyze_problem(problem, threshold_ms, limit)`。
3. `PerfettoTool` 根据问题选择模板：
   - 包含 `cpu/sched/调度/占用`：选择 `cpu_time` 模板。
   - 其他问题默认选择 `long_slice` 模板。
4. 模板生成 Perfetto SQL。
5. 继续复用 `execute_sql()` 执行 SQL。
6. 汇总 rows，生成：
   - `metrics`
   - `evidence`
   - `conclusion`
   - `recommendations`
   - 原始 `columns/rows`

### 当前边界

- `PerfettoTool` 是独立工具，尚未接入 `/chat` 的 `ExecutorAgent` 自动决策。
- `/perfetto/analyze` 当前只覆盖长耗时 slice 和 CPU time 两类模板。
- 当前结论是规则/模板生成的初步结论，不等同于完整根因分析。
- 如果 trace processor 自动下载失败，需要让服务端 Python/curl 进程能访问 Perfetto 预构建包地址，或通过 `DATAANALYZE_PERFETTO_TRACE_PROCESSOR_PATH` 指向本地 trace processor。

### 2026-05-14 方向修正：保留 trace 入库演进空间

Perfetto 链路不能被设计成“永久只查本地 output.pb 文件”。后续会存在多次采集、多份 trace、多版本性能数据对比、历史归档和前端联调场景，因此当前独立链路需要保留切换到数据库数据源的余地。

当前阶段：

- 先通过 Trace Processor 直接查询 `output.pb`。
- 先用模板跑通“性能问题 -> SQL -> 指标 -> 结论”。
- 暂不把 trace 数据抽取到 PostgreSQL。

后续阶段：

- 将采集文件登记为 dataset/trace 记录。
- 将核心 Perfetto 结果抽取到数据库事实表或指标表。
- Agent 查询时可在两类数据源之间切换：
  - `trace_processor`：直接查某个 `output.pb`。
  - `database`：查已抽取入库的 trace 结果。
- 前端联调接口必须保留 `dataset_id` / `trace_id` 这类字段，避免后续只能分析单个固定 `output.pb`。

因此，后续 `PerfettoAgent` 不应直接绑定 `output.pb` 文件路径，而应依赖一个可替换的数据源层。

### 2026-05-14 实现补充：`/perfetto/agent`

当前已新增前端联调入口 `POST /perfetto/agent`。

调用链：

1. `main.py` 接收 `PerfettoAgentRequest`。
2. `PerfettoAgent` 构建结构化 plan，保留 `dataset_id`、`trace_id`、`source_type`。
3. `PerfettoAgent` 通过 `PerfettoDataSource` 调用实际数据源。
4. 当前默认数据源为 `TraceProcessorPerfettoSource`，内部复用 `PerfettoTool` 查询 `output.pb`。
5. `PerfettoTool` 继续负责 SQL guard、Trace Processor 查询和 rows 标准化。
6. `perfetto_templates.py` 负责问题到模板 plan、SQL 构造、结果指标汇总。
7. `PerfettoReviewer` 做轻量规则审核。

当前响应结构稳定包含：

- `success`
- `dataset_id`
- `trace_id`
- `source_type`
- `plan`
- `sql`
- `metrics`
- `evidence`
- `conclusion`
- `recommendations`
- `tool_calls`
- `review`
- `error_reason`

该接口是后续前端主要联调入口。底层从 `trace_processor` 切到 `database` 时，前端请求结构应保持不变。
## 2026-05-14 补充：工具目录拆分后的当前边界

`DataAnalyze/tools` 已经从“所有工具平铺”调整为按数据源分组：

- `DataAnalyze/tools/db/`：承载原来的数据库分析链路，`DatabaseTool`、schema loader、schema selection、knowledge retrieval、query planner、field planner 都在这里。`/chat`、`ExecutorAgent`、数据库 SQL guard 继续复用这一组能力。
- `DataAnalyze/tools/perfetto/`：承载新的 Perfetto/output.pb 分析链路，`PerfettoTool` 负责 Trace Processor 查询和 Perfetto SQL guard，`perfetto_templates.py` 负责模板 plan/SQL/结果汇总，`perfetto_sources.py` 负责 `trace_processor` 与未来 `database` 数据源的切换边界。
- `DataAnalyze/tools/llm_tool.py`：仍是共享工具，暂不归入 db 或 perfetto，避免让通用 LLM 能力被错误绑定到单一数据源。

Perfetto Agent 当前调用链为：`main.py` 的 `POST /perfetto/agent` -> `PerfettoAgent` -> `PerfettoDataSource` -> `TraceProcessorPerfettoSource` -> `PerfettoTool` -> `perfetto_templates.py` 汇总指标与结论 -> `PerfettoReviewer` 规则审核。这个链路暂时查 `output.pb`，但已保留 `dataset_id / trace_id / source_type`，后续可以切换到入库后的数据库数据源。

前端联调页面：`GET /perfetto/debug`，对应文件 `DataAnalyze/web/perfetto.html`。页面可以直接填写 `session_id / problem / dataset_id / trace_id / analysis_mode / threshold_ms / limit`，调用 `POST /perfetto/agent`，并展示 summary、SQL、metrics/evidence/conclusion/review 和原始 JSON。
## 2026-05-15 当前 Perfetto 主链路状态

Perfetto LLM 链路已调整为复用原双 Agent，而不是长期维护另一套独立 Agent：

```text
/perfetto/agent(analysis_mode=llm)
 -> PerfettoAgent 响应适配
 -> ExecutorAgent(dialect="perfetto")
 -> PerfettoTool.select_schema_context()
 -> LLM 生成 Perfetto SQL
 -> PerfettoTool.validate_sql()
 -> PerfettoTool.execute_sql()
 -> ExecutorAgent 汇总结果
 -> ReviewerAgent(sql_validator=PerfettoTool.validate_sql)
 -> PerfettoAgentResponse
```

`/chat` 主链路保持不变，仍是 `ExecutorAgent + DatabaseTool + ReviewerAgent + WorkflowEngine`。

当前边界：

- `PerfettoTool` 负责 Perfetto schema、知识库召回、只读 SQL guard、trace processor 执行。
- `ExecutorAgent` 负责 schema 选择、LLM 生成 SQL、执行工具调用、结果汇总。
- `ReviewerAgent` 负责意图/结果/结论审核；Perfetto SQL 安全判断通过注入的 `sql_validator` 完成。
- `PerfettoAgent` 只做前端结构适配，保留 `dataset_id / trace_id / source_type`，为后续 `output.pb -> database` 切换留空间。
